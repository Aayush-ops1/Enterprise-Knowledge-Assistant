# Engineering Coding Standards

## 1. Languages and Tooling

### 1.1 Approved Languages
Backend services are written in Python 3.11 or newer, and frontend applications in TypeScript with React. Other languages may be used for specific components only with the approval of the platform team.

### 1.2 Formatting
All code must be formatted with Black (Python) and Prettier (TypeScript) using the repository defaults. Formatting is enforced in CI, and a formatting failure fails the build.

## 2. Version Control and Commits

### 2.1 Branching Model
The repositories follow trunk-based development: short-lived feature branches merged to main, with releases cut from tagged commits. Feature branches must be merged within 5 working days of creation.

### 2.2 Commit Messages
Commit messages must follow the Conventional Commits format, for example: `feat: add bulk export endpoint` or `fix: correct tax calculation in invoice module`. This format is required because release notes are generated automatically from commit history.

## 3. Code Review

### 3.1 Review Requirements
Every pull request requires at least one approval from a reviewer outside the author's immediate pair. The author must respond to all review comments, and re-review is required after any requested changes. CI checks, including lint, tests, and type checking, must pass before merge.

### 3.2 Pull Request Size
Pull requests should be small and focused, ideally under 400 lines of change. Large PRs must be split, or approved by the tech lead with a review plan before creation.

## 4. Testing

### 4.1 Coverage Requirements
New code must maintain at least 80% unit test coverage. Critical paths, including authentication, payment processing, and data export, require integration tests in addition to unit tests.

### 4.2 Test Types
Unit tests must run in under 2 minutes for the full suite. End-to-end tests run in the staging environment on every release candidate, and flaky tests must be fixed or quarantined within 48 hours.

## 5. Security in Code

### 5.1 Secrets Handling
Secrets such as API keys and database credentials must never be committed to source control. Secrets are stored in the company vault and injected through environment variables at deploy time.

### 5.2 Input Handling
All user input must be validated server-side and parameterised queries must be used for database access. Output rendered in the UI must be escaped to prevent cross-site scripting. Dependencies must be scanned for known vulnerabilities in CI, and critical vulnerabilities must be patched within 7 days.
