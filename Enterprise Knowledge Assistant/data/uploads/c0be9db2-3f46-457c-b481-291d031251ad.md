# Deployment Runbook

## 1. Environments

### 1.1 Environment Overview
The company maintains three environments: development (dev), staging, and production (prod). Dev is used for local and feature testing, staging mirrors production for release validation, and production serves live customer traffic.

### 1.2 Promotion Rules
Code moves from dev to staging only after the pull request is merged and CI passes. Code moves from staging to production only after the release candidate passes the automated smoke tests and the release checklist is approved by the release manager.

## 2. Release Process

### 2.1 Release Cadence
Releases are scheduled twice a week on Tuesday and Thursday. Deployments to production may only occur between 10:00 AM and 2:00 PM IST on release days.

### 2.2 Deployment Steps
The standard deployment sequence is: build the artifact, run the full automated test suite, tag the image with the version, deploy to staging, run the smoke test suite, deploy to a 5% canary of production traffic, verify metrics for 15 minutes, then roll out to 100% of traffic.

### 2.3 Feature Flags
New features must be shipped behind feature flags and can be toggled independently of deployments. This allows code to be deployed in advance of launch and rolled back instantly without a redeployment.

## 3. Database Migrations

### 3.1 Migration Rules
Database migrations must be backward compatible: columns and tables may be added but not removed in the same release that uses them. Destructive changes, such as dropping a column or table, require a separate release and approval from the data platform team.

### 3.2 Migration Timing
Migrations run automatically as part of the deployment pipeline before the new version starts serving traffic. Migrations are logged and monitored, and a failed migration automatically halts the deployment.

## 4. Rollback

### 4.1 Rollback Triggers
A deployment is rolled back if the error rate increases by more than 1 percentage point above the pre-deployment baseline, if latency exceeds the SLO for more than 5 minutes, or if a critical function is confirmed broken.

### 4.2 Rollback Procedure
The rollback procedure is to revert the code change, redeploy the previous version, and verify recovery. The target recovery time (RTO) for a rollback is 30 minutes.

## 5. Change Freeze

### 5.1 Freeze Windows
A deployment freeze applies during the last two weeks of every quarter and during major customer events. During a freeze, only emergency fixes approved by the release manager and the CTO may be deployed.

### 5.2 Freeze Exceptions
Emergency fixes during a freeze must have a documented rollback plan, be limited to the specific defect, and undergo a post-mortem review after the freeze ends.
